# Job-board company worklist

Which of the 126 companies on the watchlist reach a supported board, which do not, and what to do
about the ones that do not. Generated by probing every name against
`POST /api/connectors/job-boards/lookup` on 2026-09-04; **re-run that before trusting a row**, because
a board can move.

The console ships the working set in `frontend/src/config/companies.ts` as a checkbox list. This file
is the worksheet for everything that still needs a human to look something up.

**71 in the catalog · 11 blocked by an unsupported ATS · 22 on a custom careers API · 6 duplicates.**

Resolved from the URLs collected on 2026-09-05. ☑ is verified and shipping in
`frontend/src/config/companies.ts`; ✗ is a dead end and why. Rows still showing ☐ were never filled
in with a URL.

Two findings changed the shape of this list. **Oracle Recruiting Cloud is now supported** (`oraclehcm`)
and carries six of these employers — it was the single highest-leverage connector to add. And a handle
is often **not derivable from the company name at all**: DigitalOcean's Greenhouse token is
`digitalocean98`, Bank of America's Workday tenant is `ghr`, Akamai's Oracle pod is
`fa-extu-saasfaprod1.fa.ocs.oraclecloud.com`. No amount of guessing reaches those, which is the
argument for the catalog existing.

## How to read a careers URL

Everything in the "not working" tables below is solved the same way: open the company's careers page,
click through to the actual job list, and look at the address bar. The URL says which ATS it is and
what the handle must be.

| URL you land on                                                | Platform        | Paste this                                        |
|----------------------------------------------------------------|-----------------|---------------------------------------------------|
| `boards.greenhouse.io/acme` or `job-boards.greenhouse.io/acme` | Greenhouse      | `acme` (or `greenhouse:acme` to pin)              |
| `jobs.lever.co/acme`                                           | Lever           | `acme` (or `lever:acme`)                          |
| `jobs.ashbyhq.com/acme`                                        | Ashby           | `acme` (or `ashby:acme`)                          |
| `careers.smartrecruiters.com/Acme`                             | SmartRecruiters | `Acme`                                            |
| `acme.wd5.myworkdayjobs.com/External_Careers`                  | Workday         | **the whole URL**, or `acme/External_Careers/wd5` |
| anything else (custom careers site)                            | own ATS         | nothing — needs a new connector, see below        |

Paste it into the **Check** box on the Add-a-source form first. `found: true` with a sensible posting
count means it works; then add it. A handle that is merely wrong and a company that is genuinely not
on that platform both come back `found: false` — the API cannot tell them apart
(`BoardPlatform.countPostings` returns empty for both, deliberately), so a miss is never proof of
absence.

## Not working — Workday, no code needed (37 left)

Workday **is already supported**. It is the one platform that cannot be resolved from a bare company
name — Workday hands each customer an arbitrary site slug on an arbitrary numbered pod, and 13 of 22
blind attempts failed on that alone, which is why it is not probed during resolution. Read the triple
off the careers URL and it works immediately; verified live against Adobe
(`adobe/external_experienced/wd5` → 727 postings, and the pasted URL form works too).
[`job-discovery.md`](./job-discovery.md) already records Accenture, Walmart, IBM, Visa and Qualcomm as
Workday tenants — those misses were always wrong URL guesses, never absent boards.

### The careers URL is usually the wrong URL

Most large employers front Workday with a vanity domain — Mastercard's job pages are served from
`careers.mastercard.com`, which names neither the tenant (`mastercard`) nor the pod (`wd1`) nor the
site (`CorporateCareers`). Pasting that address does nothing: it parses as an ordinary company name,
gets probed against the four bare-name platforms, and misses.

**The Apply button gives it away.** Open any job on the vanity site and click Apply — or just
right-click it and copy the link. It goes to the real Workday address:

```
mastercard.wd1.myworkdayjobs.com/CorporateCareers/job/Vadodara-India/Senior-Software-Engineer_R-286206-1/apply
└─ tenant  └─ pod                └─ site
```

giving `mastercard/CorporateCareers/wd1` — 1080 postings, verified. Faster still: view source on the
job page and search for `myworkdayjobs`.

### Check the size before you add one

The poll cost is `1 + N` requests over the whole site, every cycle, and it is not reduced by the
location filter — Workday's search results carry a bare city or `"5 Locations"` with no place, so the
connector has to fetch everything and filter afterwards. The lookup's posting count is therefore a
direct estimate of what each poll will cost:

| Verified so far | Triple                            | Postings | Verdict                                                   |
|-----------------|-----------------------------------|----------|-----------------------------------------------------------|
| Adobe           | `adobe/external_experienced/wd5`  | 727      | fine on a slow schedule                                   |
| Mastercard      | `mastercard/CorporateCareers/wd1` | 1,080    | fine on a slow schedule                                   |
| Lowe's          | `lowes/LWS_External_CS/wd5`       | 12,425   | **think twice** — ~12k requests per poll, tens of minutes |

Rough rule: under ~1,500 is comfortable at the default 3-hour cadence; a few thousand wants a daily
schedule; five figures wants a deliberate decision, because one such source can dominate every poll.
The location filter still bounds everything *downstream* — entities, chunks and embeddings — so a huge
board is a fetch problem, not a storage or embedding one.

**Before you add many of these, read this:** Workday costs `1 + N` requests over the *whole* site per
poll, and ignores the location filter while fetching, because its search results give a bare city or
`"5 Locations"` with no place at all. Adobe alone is ~728 requests and takes minutes. Add them a few
at a time and consider a slower schedule for that source.

## Not working — own ATS, needs a new connector (21)

These run their own careers stack. No handle reaches them; each needs an `@ApplicationScoped`
`BoardPlatform` bean (`id()`, `countPostings()`, `fetch()` — discovered by CDI, registered nowhere,
see `docs/connectors.md`). Roughly 150 lines each plus normalisation.

They are not equally worth it. Some publish clean JSON that a connector can read directly — Amazon
(`amazon.jobs/search.json`) and Microsoft (`gcsservices.careers.microsoft.com` search) are the best
value, being large boards behind a stable public API. Others are client-rendered apps with no public
endpoint; those would need scraping and would break often, and are better left out than shipped
fragile.

## Adding a verified company to the catalog

One line in `frontend/src/config/companies.ts`, sorted by label:

```ts
{
    label: 'Acme', handle
:
    'acme', platform
:
    'greenhouse'
}
,
```

`handle` is the bare name, never a pinned `platform:handle` — a bare name is re-probed against every
platform at discovery, so a company that moves ATS can be recovered by re-saving the source. `platform`
is display only. Nothing goes in this file that has not returned `found: true` from the lookup endpoint.
